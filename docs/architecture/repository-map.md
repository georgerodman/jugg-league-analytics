# Repository Map

This document explains where project files belong and how the major parts of
the JUGG draft application relate to one another. Update it whenever a new
top-level area or architectural boundary is introduced.

## Top-level structure

```text
jugg-league-analytics/
├── app/                    Next.js routes, layouts, styles, and API endpoints
├── src/                    TypeScript application and draft runtime
│   ├── ui/                 Draft-room React components
│   ├── server/             Server actions/API adapters and database wiring
│   └── domain/             Framework-independent draft rules
├── db/
│   └── migrations/         Ordered SQLite schema migrations
├── scripts/                Python acquisition, modeling, and rebuild commands
├── data/
│   ├── raw/                Immutable source snapshots
│   └── processed/          Versioned normalized/model artifacts
├── config/                 League rules and reviewed identity overrides
├── docs/
│   ├── README.md           Documentation index and filing guide
│   ├── PROJECT_SPEC.md     Durable project-wide source of truth
│   ├── product/            User-facing requirements and decision guidance
│   ├── history/            Compact records for completed seasons
│   ├── architecture/       Technical boundaries and contracts
│   └── operations/         Repeatable refresh and maintenance procedures
├── tests/
│   ├── domain/             TypeScript domain/runtime tests
│   └── test_*.py           Python pipeline and SQLite-schema tests
├── package.json            Pinned Node dependencies and commands
├── package-lock.json       Exact reproducible Node dependency graph
├── requirements-data.txt   Pinned Python data dependencies
└── node_modules/           Generated third-party Node packages only
```

The `.local/` directory contains ignored operational SQLite state created while
running the draft room. The `.next/` directory and `node_modules/` are generated
and ignored.

`config/active-season.json` is the single runtime selector for the current
season, draft ID, local database, and Google Sheets mapping. It must be changed
only through the validated season-rollover workflow; a rollover must never
reuse or mutate a finalized season's database.

## Authored code versus generated files

Project-authored files belong in `src/`, `db/`, `scripts/`, `config/`, `docs/`,
and `tests/`. Never place or edit project code under `node_modules`; that folder
is generated by `npm install` and may be deleted and recreated at any time.

Raw provider snapshots are immutable. Processed artifacts are also immutable
within their timestamped build directories. A `latest.json` pointer identifies
the current validated build. Do not edit generated CSV or JSON model output by
hand; change its source, adapter, configuration, or model and run the guarded
rebuild instead.

## Application dependency direction

```text
Next.js route in `app/` or component in `src/ui/`
        ↓
server action or API adapter
        ↓
domain service
        ↓
SQLite
        ↓
sync outbox → optional Google Sheets adapter
```

- `app/` and `src/ui/` may call `src/server/` boundaries through API routes.
- `src/server/` translates HTTP/UI inputs into typed domain commands.
- `src/domain/` owns rules, invariants, transactions, and state transitions.
- Domain code must not import React, Next.js, Google APIs, or AI services.
- Essential draft actions commit to SQLite before optional synchronization.
- UI and external adapters must not write draft tables directly.

Current domain files:

- `src/domain/DraftService.ts` — transactional draft commands and recovery
  auditing.
- `src/domain/importDraftArtifacts.ts` — validated model/owner artifact import
  and 2026 roster-slot initialization.
- `src/domain/liveDecisionEngine.ts` — offline strategy-neutral roster
  completions, shadow price ladders, decision bands, and live league outlook.

Current application files:

- `app/page.tsx` and `app/layout.tsx` — canonical Next.js entry points for the
  draft board.
- `app/board/page.tsx` — compatibility redirect from `/board` to `/`.
- `app/api/draft/route.ts` — validated local draft read/mutation API.
- `src/ui/board/DraftBoard.tsx` — canonical draft-board interface and
  interactions, with styles isolated in `DraftBoard.module.css`.
- `src/server/draftStore.ts` — SQLite lifecycle, artifact bootstrap, view-model
  queries, and translation to deterministic domain commands.

## Data and modeling dependency direction

```text
data/raw
   ↓
source-specific Python adapters
   ↓
data/processed source artifacts
   ↓
canonical projections and identities
   ↓
price, probability, production, and owner models
   ↓
combined draft artifacts
   ↓
SQLite artifact import
```

Python modeling code must not become a live draft dependency. Draft night uses
only validated local artifacts imported before the draft.

## Database organization

- `db/migrations/001_initial.sql` defines the first offline draft schema.
- `db/migrations/002_strategy_and_market_context.sql` adds ADP, bye week, and
  persistent Renegades strategy preferences.
- Add future migrations as `002_description.sql`, `003_description.sql`, and so
  on; never rewrite an applied migration.
- SQLite is authoritative during the draft.
- Immutable events plus transactional materialized state provide auditability
  and fast reads.
- Corrections append compensating events rather than deleting history.

The domain contract is documented in
`docs/architecture/draft-domain-and-sqlite.md`.
The durable product scope and screen contract are documented in
`docs/PROJECT_SPEC.md` and the focused documents under `docs/product/`.
Completed-season decisions and validation evidence are summarized under
`docs/history/`; detailed superseded material remains available at the season's
final Git tag.
The plain-language product interpretation and intended draft-night use are in
`docs/product/draft-decision-guide.md`.
The live TypeScript decision engine owns roster paths, recommendation bands,
and draft-state recalculation. Completed standalone 2026 championship studies
were retired after their accepted conclusions were preserved in the season
record and final Git tag.

## Scripts and operational commands

Python filenames use `snake_case.py`. Scripts should have one clear operational
purpose and expose a command-line entry point when directly runnable.

Important commands:

```sh
python3 scripts/season_refresh.py --season 2027 # dry-run annual refresh plan
python3 scripts/owner_tendencies.py # owner profiles only
npm run typecheck                   # strict TypeScript verification
npm run test:domain                 # offline domain-engine tests
npm run dev                         # local Renegade Draft Room
npm run build                       # production application build
python3 -m unittest discover -s tests -q
```

The complete source-refresh and rebuild runbook is
`docs/operations/data-source-operations.md`.
The completed preservation and pruning record is in
`docs/history/2026-season-record.md`.

## Naming conventions

| Area | Convention | Example |
| --- | --- | --- |
| TypeScript service/class modules | `PascalCase.ts` | `DraftService.ts` |
| React components | `PascalCase.tsx` | `NominatedPlayerCard.tsx` |
| Next.js framework files | framework lowercase | `page.tsx`, `layout.tsx` |
| General TypeScript utilities | descriptive `camelCase.ts` | `formatPrice.ts` |
| Python modules and scripts | `snake_case.py` | `production_value_model.py` |
| SQL migrations | zero-padded number + description | `001_initial.sql` |
| Documentation | descriptive lowercase kebab-case | `owner-tendencies.md` |
| Generated builds | UTC timestamp directory | `20260823T194952Z/` |
| Current artifact pointer | `latest.json` | `owner_tendencies/latest.json` |

Use stable domain terms consistently: `draft`, `team`, `owner`, `player`,
`nomination`, `sale`, `roster slot`, `event`, and `sync outbox`. Do not call a
sale a bid; the application intentionally records only the final result.

## Tests

- Put TypeScript domain tests under `tests/domain/`.
- Put Python pipeline and schema tests under `tests/test_*.py`.
- Future UI component tests should live beside or clearly mirror the component
  structure; choose one convention when the UI scaffold is created and record
  it here.
- Every domain invariant, migration, model calculation, recovery path, and sync
  failure mode requires a focused test.

The guarded rebuild runs both Python and TypeScript verification before it
publishes current artifacts.

## Adding a new file

Before creating a file, identify its responsibility:

- Next.js route or global styling → `app/`
- UI rendering or interaction → `src/ui/`
- request/database wiring → `src/server/`
- draft rule or state transition → `src/domain/`
- schema change → `db/migrations/`
- static data/model work → `scripts/`
- league or identity configuration → `config/`
- durable explanation/runbook → `docs/`
- generated source/model data → `data/raw/` or `data/processed/`
- third-party dependency → declare it in the appropriate package file; never
  copy it manually into `node_modules`

If a file appears to belong in multiple layers, split the responsibilities so
the dependency direction remains clear.
